# 15 — System Architecture Blueprint & Decision Matrix

*Repository strategy, service topology, fault isolation, deployment, and the Day-1 → scale roadmap for Regulars. Binding where it says so; the rest is the reasoning so nobody relitigates it in month three. Companion diagram: `docs/15-system-design.png`. Stack facts live in `02`; data in `03`; build order in `10`.*

**The one-paragraph answer.** One monorepo (npm workspaces + Turborepo). One codebase, **two deployable processes**: `api` (HTTP + Socket.IO, tenant-scoped, latency-critical) and `worker` (BullMQ consumers, crons, CDC export). A **modular monolith** inside both — strict module boundaries, service-to-service calls only, side effects through the Postgres outbox (`app.events`). Every third party (Meta WhatsApp, Razorpay/Cashfree, LLM, OCR) sits behind an adapter and is called **only from the worker**, in its **own queue with its own concurrency, rate limit, circuit breaker and DLQ**. Webhook ingress is a 30 ms write-and-202. If Meta is down, orders keep flowing; if the LLM is slow, bills keep printing; if Redis dies, ordering still works and queued work replays from the outbox. One Postgres (Supabase) with three schemas and RLS; database-per-service only when a module actually leaves the process. Docker Compose on one VPS on Day 1; the same images run on Fly/ECS at 50+ outlets without a code change.

## 1. Repository strategy

### 1.1 Monorepo vs polyrepo

| | Monorepo (npm workspaces + Turborepo) | Nx monorepo | Polyrepo (repo per app/service) |
|---|---|---|---|
| Shared types / zod / enums | One `packages/shared`; a schema change and every consumer compile in one PR | Same, plus generators | Publish a package, bump versions in N repos, drift is guaranteed |
| Atomic changes (API + owner-web + customer-web) | One PR, one review, one CI run | Same | Three PRs, coordinated deploys |
| CI cost | Turborepo caches by content hash; only affected packages build/test (`--filter=...[origin/main]`) | Best-in-class affected graph, heavier config | N pipelines, N copies of setup |
| Cognitive load for 3 people | Low — one `npm install`, one lint config, one `CLAUDE.md` | Medium — Nx generators/executors are a second framework | High — N CLAUDE.md, N configs, N dependabots |
| AI codegen quality | High — Claude Code sees the whole graph and the shared schemas | High | Low — the model can't see the consumer of the type it changes |
| Team scaling (10–30 engineers) | CODEOWNERS per `apps/*` and `modules/*`; Turborepo remote cache | Nx shines here (module boundary lint, affected e2e) | Only wins when teams genuinely never touch each other's code |
| Extraction of a service later | Copy `modules/x` + `packages/shared` into `apps/x-service` — same repo | Same | Already separate, but you paid for it every day before you needed it |

**Decision (binding): monorepo, npm workspaces + Turborepo.** Nx is the upgrade path if module-boundary lint via ESLint (`no-restricted-imports`) stops being enough — that is a config change, not a migration. Polyrepo is rejected: for a 3-person AI-assisted team the shared-schema drift alone would cost more than every other decision here combined.

### 1.2 How code is shared (and what is not)

| Package | Contains | Consumed by | Rule |
|---|---|---|---|
| `packages/shared` | Zod schemas (API DTOs), enums re-exported from `db/schema.ts` (Postgres enums → TS unions via `drizzle-zod`), error codes, order-state machine, money/phone/date utils, event payload schemas (`docs/03` §3.3), `ToolExecutionContext`, WhatsApp normalised payload | api, worker, 4 frontends | Pure TS, zero runtime deps beyond zod. No Express, no Drizzle, no React |
| `packages/db` | `schema.ts` + `relations.ts` (generated by `drizzle-kit pull`), `client.ts` (`withTenant`, `asWorker`), migrations, seed | api, worker | The only package that imports `drizzle-orm` / `pg`. Frontends never see it |
| `packages/ui` | Table badge, customer badge, status pill, stat tile, drawer, sheet (the patterns in `docs/14` §4.1) + design tokens | owner-web, customer-web, admin-web, site | React + Tailwind preset; no data fetching |
| `packages/config` | ESLint (incl. the custom rules: no `db` in services, no `asWorker` outside `jobs/`, no `req.*.vendorId`), tsconfig bases, Prettier, Tailwind preset | everything | |
| `packages/api-client` | Generated from the zod route schemas: typed fetchers per module + TanStack Query hooks | frontends | Generated in CI from `apps/api`; never hand-edited |

What is **not** shared: business logic. `modules/orders/orders.service.ts` is imported by nothing outside `apps/api` and `apps/worker` (which share the `modules/` tree — see §5). A frontend that "just needs the pricing rule" gets a `packages/shared` pure function, not the service.

### 1.3 Velocity vs team scaling

- 1–5 engineers (now): everyone commits to `main` behind PRs; Turborepo local cache; one CI workflow with `turbo run lint test build --filter=...[origin/main]`.
- 5–15: CODEOWNERS on `apps/*` and `apps/api/src/modules/*`; Turborepo remote cache (Vercel or self-hosted); module-boundary ESLint rules become errors.
- 15+: Nx if you want enforced project graphs and per-module CI; or extract the first real service (§4) — the repo shape doesn't change either way.

## 2. Service architecture & fault isolation

### 2.1 Topology options

| | Modular monolith (one process) | **Modular monolith + isolated worker(s)** ← ours | Microservices from Day 1 |
|---|---|---|---|
| Deployables | 1 | 2 (api, worker) growing to 3–4 by queue group | 8–12 |
| Cascade risk | High: a stuck Meta call, a 30-s PDF or an LLM retry storm eats the same event loop as order placement | Low: anything slow or third-party runs in the worker; the API only touches Postgres and Redis | Low, if you also build the plumbing (service discovery, retries, tracing, per-service CI) |
| Transactions | Native | Native (same Postgres) | Distributed — sagas for "place order + decrement stock" |
| Ops for 3 people | Trivial | Trivial (+1 container) | Self-harm (docs/10 A1) |
| Extraction later | Rewrite | Copy a module into a new process, swap the in-process call for a queue/HTTP call (§4) | n/a |

**Decision (binding): modular monolith, two processes, strict boundaries.** Same Docker image, different entrypoint (`node dist/api.js` / `node dist/worker.js`). The worker is split further by queue group when a group needs its own resources (§2.3), still from the same image.

### 2.2 Fault domains (zero-cascade rules)

The system has five fault domains. Nothing in a lower row may block a higher row.

| # | Domain | Runs in | Depends on | If it fails |
|---|---|---|---|---|
| 1 | **Ordering & billing** (scan → menu → round → accept → settle) | api | Postgres | — this is the product; everything else is designed so this never waits on it |
| 2 | **Real-time** (Socket.IO rooms) | api | Redis adapter (only when > 1 API instance) | Clients fall back to 30-s polling; nothing is lost |
| 3 | **Ingress** (webhooks: WhatsApp statuses/inbound, gateway callbacks) | api (thin) | Postgres | Signature check → `webhook_dedupe` → `webhook_events` raw → 202. No parsing, no business logic, no third-party calls. Processing is a job |
| 4 | **Outbound integrations** (Meta sends, gateway refunds, LLM, OCR, PDF, e-bill, exports) | worker, per-queue | Redis + the third party | Queue backs up; DLQ after retries; circuit breaker opens; the API never notices |
| 5 | **Analytics & ML** (features, CDC export, insights, briefing build) | worker (`features` group) | Postgres read replica later, lake | Insights are late. Nobody's order is late |

Mechanics that enforce the rows:

1. **The API never calls a third party.** The only network calls from `apps/api` are Postgres, Redis, and (for uploads) presigned-URL generation. Lint rule: `modules/**` may import `adapters/**` interfaces, not implementations; implementations are wired in `apps/worker`. The one exception — creating a gateway payment request when the customer taps Pay — is a **2-s timeout + fallback to "pay at counter"** (docs/05 §11.5), and even that moves to the worker with a pending state if the gateway's p95 ever exceeds 800 ms.
2. **Transactional outbox.** Every business change writes `app.events` in the same transaction (`docs/03` §4.5). Workers consume events, not API calls. If Redis is wiped, the `events` watermark replays; if a worker dies mid-job, BullMQ redelivers; idempotency keys (`message_dedupe`, `automation_runs.idempotency_key`, `tool_executions.idempotency_key`) make the redelivery a no-op.
3. **Bulkheads per queue.** Each queue has its own worker concurrency, rate limiter (Meta: N msgs/s per channel; LLM: cost budget per vendor per day), timeout, retry policy and DLQ. A Meta outage fills the `whatsapp` queue; the `payments` queue keeps confirming captures.
4. **Circuit breakers** (opossum) around every adapter: open after 5 failures / 30 s, half-open probe, and a `health` gauge the admin panel shows. While open, sends stay `queued` — never `failed`.
5. **Timeouts everywhere**: Postgres statement_timeout 5 s (api) / 60 s (worker); HTTP to third parties 10 s; LLM 30 s; OCR 60 s. No unbounded await.
6. **Load shedding**: the API's rate limiter fails **closed** on auth routes and **open** elsewhere if Redis is down (docs/06 §6). Order placement does not need Redis at all.
7. **Poison-message hygiene**: a job that fails 5× goes to the DLQ with the full payload; a DLQ growth alert pages; the admin panel has "retry" and "discard". Nothing loops forever.
8. **Separate process = separate memory.** A PDF export that leaks memory kills the worker container, which restarts in 3 s; the API's heap is untouched. This is the whole reason for process #2.

### 2.3 Asynchronous messaging

| Option | Fit | Verdict |
|---|---|---|
| **BullMQ on Redis** | Delayed jobs, repeatable crons, rate limiters, priorities, DLQ, retries with backoff, per-queue concurrency, Node-native, one dependency we already run (OTP, rate limits, Socket.IO adapter) | **Chosen.** Everything the pipeline in `docs/02` §8 needs, zero new infra |
| Redis Streams | Consumer groups, replay | Lower-level than BullMQ; we'd rebuild retries/DLQ. Only if we needed ordered fan-out to many consumers — we don't; the outbox gives replay |
| RabbitMQ | Routing, real broker semantics | Another stateful service to run for a 3-person team; no feature we need that BullMQ lacks |
| SQS / Cloud Tasks | Managed, durable | Ties us to a cloud; no delayed-repeatable crons without more services; fine later if we move to AWS |
| pg-boss (Postgres-backed queue) | Removes Redis as a dependency for queues | Real option: durable by default, transactional enqueue in the same txn as the outbox. Rejected only because Redis stays anyway (rate limits, OTP, sockets) and BullMQ's rate limiter is what the Meta cap needs. Revisit if Redis becomes the flakiest piece |

**Queues (binding names)** — one BullMQ queue per fault domain, each with its own worker group:

| Queue | Jobs | Concurrency / limits | Retry → DLQ |
|---|---|---|---|
| `events` | outbox fan-out: read `app.events` by watermark → dispatch to the queues below + Socket.IO emits | 1 consumer per partition of `vendor_id` hash (ordered per tenant) | replay from watermark |
| `whatsapp` | template sends (OTP, e-bill, status, campaigns, triggers, briefing) | 10 workers; rate limiter per channel (Meta tier); priority: otp > utility > marketing | 5× backoff 30 s→10 min → DLQ; 131049 → skipped, no retry |
| `webhooks` | process raw `webhook_events` (normalise → messages / payments / conversations) | 5 workers | 5× → DLQ; reprocess from admin |
| `payments` | gateway refund calls, pending-payment reconcile (every 3 min), settlement checks | 3 workers; breaker per provider | 5× → DLQ + alert (money) |
| `ai` | owner-bot turns, briefing text (LLM), campaign copy (v1.5), RAG re-embed | 4 workers; per-vendor daily cost budget; 30-s timeout | 2× → reply "try again later" (never DLQ silently) |
| `ocr` | menu photo/PDF extraction | 2 workers; 60-s timeout | 2× → import status failed with reason |
| `exports` | vendor export zip, QR PDF sheet, day-close PDF (v1.1) | 2 workers; memory-heavy → own container at scale | 3× → failed with reason |
| `automations` | trigger evaluation per event, campaign scheduling, holdout assignment, attribution | 5 workers | idempotent by `automation_runs.idempotency_key` |
| `features` | segment recompute, `ml.customer_features`, `ml.outlet_features`, dead-hour detection, insights, briefing build, CDC → parquet | 2 workers; runs at 03:00–05:00 IST | 3× → alert; never blocks anything |
| `housekeeping` | partition roll, dedupe-table cleanup, insight expiry, session archive, order auto-expiry (every minute), overnight-tab audit | 1 worker | 3× → alert |

Rules: a job payload is an **id + intent**, never a document (the worker re-reads the row — stale payloads are how double sends happen). Every handler is idempotent. Every queue has a max-age (jobs older than 24 h are dropped with a log, except `payments`).

### 2.4 Synchronous boundaries the API does keep

Order placement, stock decrement, invoice numbering, coupon caps, RLS-scoped reads — all synchronous, all Postgres, all < 15 ms. That is the point: the critical path touches one database and nothing else.

## 3. Deployment & infrastructure

### 3.1 Runtime platform

| | Docker Compose on one VPS (Day 1) | Fly.io / Railway (PaaS containers) | AWS ECS Fargate | Serverless (Lambda / Vercel functions) |
|---|---|---|---|---|
| Fit for Socket.IO + BullMQ workers (long-lived processes) | Yes | Yes | Yes | **No** — no long-lived connections, cold starts on the order path, workers need a separate service anyway |
| Ops burden | 1 machine, 4 containers, Caddy auto-TLS | Near zero; per-process scaling; Mumbai region (Fly `bom`) | Real IAM/VPC/ALB setup; 2–3 days of work | Low, but the architecture doesn't fit |
| Cost at 50 outlets | ~₹4–6k/mo | ~₹8–15k/mo | ~₹20k+/mo | n/a |
| Path to next step | `docker compose` → same images on Fly/ECS | → ECS/K8s if ever needed | — | — |

**Decision: Docker Compose on one VPS (Mumbai) for pilot → Fly.io (or ECS) at > ~50 outlets or the first time you need a second API instance.** Same Dockerfile, same images, same env contract; the move is a day. Serverless is rejected for the API (sockets, pooler, workers) but fine for the public site (static) and the future e-bill PDF renderer if it ever needs burst.

```
VPS (4 vCPU / 8 GB, Mumbai)
├── caddy        :443  auto-TLS, reverse proxy, websocket pass-through
├── api          :4000 node dist/api.js   (2 replicas when CPU > 60 %; Socket.IO Redis adapter on)
├── worker             node dist/worker.js --queues=events,whatsapp,webhooks,payments,automations,housekeeping
├── worker-heavy       node dist/worker.js --queues=ai,ocr,exports,features   (own memory limit; first to move to its own machine)
└── redis        :6379 persistence on (AOF) — ephemeral by contract, but survives restarts
Supabase (managed, ap-south-1): Postgres 16 + pgvector + pg_cron, pooler (6543) + direct (5432), Storage, PITR
Static hosting/CDN: owner-web, customer-web, admin-web, site (Cloudflare Pages / Vercel static)
```

### 3.2 Data tier boundaries

| | Shared DB, shared schema | **Shared DB, separate schemas + RLS** ← ours | Database per service |
|---|---|---|---|
| Transactions across modules | Yes | Yes (same DB) | No — sagas |
| Isolation | None | Schemas `app` / `ml` / `ops`; roles `regulars_app` (RLS) / `regulars_worker` / `regulars_ml` (read-only); partitions for ledgers | Full, at the cost of joins and consistency |
| Analytics load on OLTP | Shared | Read replica for `regulars_ml`; heavy ledgers partitioned; lake via CDC | Separate by construction |
| Migration path | — | A module that extracts takes its tables to its own schema first (`ALTER TABLE … SET SCHEMA`), then to its own database when it actually needs it | — |

**Decision (binding): one Postgres, three schemas, RLS as the tenant wall** (`docs/03`). Database-per-service is a consequence of extraction (§4), never a starting point. The first data split will be a **read replica** for reports/ML, not a second write database.

Storage: Supabase Storage (menu photos, QR PDFs, exports, parquet lake) via presigned URLs — the API never proxies bytes.

### 3.3 Environments, CI/CD, observability

- **Envs:** `local` (docker-compose: postgres 16 + pgvector, redis, mailhog-style WhatsApp stub) · `staging` (second Supabase project; VPS #2 or Fly app) · `prod`.
- **CI (GitHub Actions):** `turbo run lint typecheck test --filter=...[origin/main]` → integration tests against a Postgres service container with migrations + RLS → `docker build` one image → push → `deploy staging` on merge to `main` → manual promote to prod. Migrations run **before** the new image starts (`drizzle-kit migrate` with the direct URL); forward-only; rollback = PITR + previous image.
- **Observability:** pino JSON logs with `requestId`/`vendorId`/`jobId` → Loki or Better Stack; Sentry on api/worker/frontends; Prometheus-style gauges via `/metrics` (queue depth, DLQ size, breaker state, replication-slot lag, DEFAULT-partition rows, p95 per route); UptimeRobot on `/healthz`; alerts to the team WhatsApp group.
- **Secrets:** env only, parsed at boot (`config/env.ts`); gateway/WABA credentials referenced by `*_ref` columns and resolved from the secret store inside adapters.

## 4. Evolutionary roadmap — Day 1 to scale

### 4.1 Boundary rules that make extraction cheap (binding, Day 1)

1. **A module is a folder** `apps/api/src/modules/<name>/` with `routes · controller · service · tools · events · repo (optional) · test`. It owns its tables (listed in `<name>.owns.ts`) and nobody else writes to them.
2. **Cross-module calls are `service → service` through the module's `index.ts` public interface**, passing the same `tx`. Importing another module's internals (`../orders/orders.repo`) is a lint error (`no-restricted-imports` by path).
3. **Side effects cross modules only as events** (`app.events` outbox → worker). A module never enqueues jobs for another module directly.
4. **Every third party is an adapter**: `adapters/<vendor>/` implements a port interface from `adapters/ports/` (`NotificationService`, `PaymentProvider`, `LlmProvider`, `OcrProvider`, `StorageProvider`). Modules depend on ports only.
5. **Every owner action is a `tools` entry** with a JSON-schema input — that is already a network-ready contract.
6. **No shared mutable state** in process memory (no in-memory caches of tenant data; Redis or Postgres only).
7. **Config per module** in `config/env.ts` namespaces (`WHATSAPP_*`, `PAYMENTS_*`) so an extracted service takes only its own variables.

### 4.2 The 2-hour extraction recipe

Say `whatsapp` becomes its own service (the realistic first candidate: Meta rate limits + per-vendor WABA make it want its own scaling).

| Step | Time | What |
|---|---|---|
| 1 | 10 min | `apps/whatsapp-service/` = copy of `apps/worker` entrypoint that registers only `modules/whatsapp` + its adapters. Same image build, new Dockerfile target |
| 2 | 20 min | Its tables move: `ALTER TABLE app.messages, app.conversations, app.message_dedupe, app.whatsapp_channels, app.message_templates SET SCHEMA whatsapp;` — same DB, own schema, own role. Drizzle `pull`, commit |
| 3 | 30 min | Inbound: the service consumes the `whatsapp` queue (unchanged) and the `events` fan-out delivers to it (unchanged). Outbound: the two in-process calls other modules make (`NotificationService.send`, `conversations.getWindow`) become HTTP calls to the service's `/internal/*` routes — the port interface is identical, only the implementation in `adapters/ports` changes to an HTTP client with the same zod schema |
| 4 | 20 min | Webhook route `/webhooks/whatsapp` moves to the service (Caddy path rule). `webhook_events` for source `whatsapp` writes to the new schema |
| 5 | 20 min | Compose/Fly: new process, env namespace `WHATSAPP_*`, health check. Deploy. Old module folder deleted from `apps/api` |
| 6 | 20 min | Leak-matrix + integration tests green; dashboards show the new queue owner |

Nothing in `orders`, `billing`, `customers` changes. Own database later (`pg_dump` the schema → new instance → change one connection string) if and only if the service's write load justifies it.

### 4.3 Scale ladder (each step only when a metric says so)

| Trigger | Step | Code change |
|---|---|---|
| API CPU > 60 % sustained | 2 API replicas + Socket.IO Redis adapter | 0 (env flag) |
| Worker memory spikes from OCR/exports | `worker-heavy` on its own machine | 0 (compose) |
| Reports slow the desk | Supabase read replica; `regulars_ml` + reports route to it | 1 connection string |
| > 500 outlets, > 200 M events | partitions detach to the parquet lake; DuckDB/Athena for ML | 0 (already designed) |
| Meta per-vendor WABA (v1.5) | extract `whatsapp` (§4.2) | 2 h |
| LLM traffic dominates cost/latency | extract `agents` the same way; add a per-vendor token bucket | 2 h |
| Multi-region / hotels chain | Fly multi-region for API; Postgres stays single-writer in Mumbai | 0 |

Things that are **not** on the ladder: Kubernetes, microservices-by-default, a second write database, GraphQL, a service mesh.

Two details that matter:

- **`modules/` is one tree used by both processes.** `apps/api` registers routes + controllers; `apps/worker` registers consumers + crons; both call the same services. Implement it as a workspace package (`packages/modules`) if the symlink bothers Turborepo's cache — the boundary rules are identical either way.
- **`adapters/ports` is the seam.** Today the port is implemented by an in-process class; after extraction it is implemented by an HTTP client with the same zod contract. Modules never notice.

## 6. Decision matrix (summary)

| Decision | Choice | Revisit when |
|---|---|---|
| Repo | Monorepo, npm workspaces + Turborepo | Module-boundary lint insufficient → Nx |
| Topology | Modular monolith; `api` + `worker` (+ `worker-heavy`) from one image | A module needs independent scale → extract (§4.2) |
| Messaging | BullMQ on Redis; Postgres outbox as the durable source | Redis becomes the flakiest piece → pg-boss |
| Third parties | Adapters behind ports; called only from the worker; breaker + bulkhead per queue | Never |
| Ingress | Thin webhook write-and-202; processing async | Never |
| Database | One Postgres (Supabase), schemas `app/ml/ops`, RLS; partitions; pgvector | Read replica first; DB-per-service only after extraction |
| Platform | Docker Compose on a Mumbai VPS → Fly.io/ECS with the same images | > 50 outlets or second API instance |
| Serverless | Static frontends only | Never for api/worker |
| Real-time | Socket.IO, emit-after-commit from the worker, 30-s polling fallback | > 1 API instance → Redis adapter (env flag) |
| AI | Behind `LlmProvider`; own `ai` queue with per-vendor budget; owner bot reads only in v1 | LLM cost/latency dominates → extract `agents` |
