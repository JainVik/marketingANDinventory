# 02 — System Architecture

Binding technical blueprint for v1. Product scope lives in `01-product-scope.md`; data shapes in `03-database-schema.md`; endpoints in `04-api-contract.md`.

## 1. Stack (fixed — do not substitute)

| Layer | Choice | Notes |
|---|---|---|
| Runtime | Node.js 22 LTS, TypeScript strict mode everywhere | No plain JS files |
| API framework | Express 5 | Layered MVC (below) |
| DB | **PostgreSQL 16 on Supabase** (pgvector, pg_cron, pg_partman available) via **Drizzle ORM** | SQL migrations are the source of truth (`db/migrations/`); `db/schema.ts` is generated by `drizzle-kit pull`. Row-Level Security is the tenant wall (§4) |
| Cache / queues | Redis 7 + BullMQ | WhatsApp queue, OTP store, rate-limit counters, job retries. Ephemeral only |
| Real-time | Socket.IO (server + owner desk + customer status page) | Polling fallback built in; emit after commit |
| Frontend | React 18 + Vite + TypeScript; TanStack Query; Zustand for the little client state; Tailwind | No Redux |
| Validation | Zod — single source of truth, shared between API and frontends; DB enums flow in via `drizzle-zod` | No Joi |
| Auth | Own JWT: access (15 min) + rotating refresh (30 days, httpOnly cookie); customers by phone OTP, owners by email+password | Not Supabase Auth (§6) |
| WhatsApp | Meta WhatsApp Business Platform (Cloud API) — platform channel in v1, per-vendor WABA in v1.5 | Behind our own `NotificationService` interface |
| Payments | Gateway adapter interface (`PaymentProvider`): Razorpay + Cashfree adapters; **restaurant is merchant of record**; we create requests and consume webhooks | Money never touches us |
| AI | Model calls behind `LlmProvider` interface; RAG on pgvector; owner bot read-only via the `tools` registry | See §9 |
| Tests | Vitest + Supertest against real Postgres (testcontainers / docker-compose), migrations applied, RLS on | Coverage gates in CLAUDE.md |
| Deploy v1 | Docker Compose on one VPS (api, worker, redis, caddy) + Supabase (DB, Storage) + frontends on static hosting/CDN | 12-factor: config only via env |

**Rule:** anything used by ≥ 2 apps lives in `packages/shared`. Order-state enums, zod schemas, and error codes are NEVER redeclared per app. DB enums are imported from `db/schema.ts` into shared, not retyped.

## 3. Backend module pattern (layered MVC)

Every domain module has exactly this internal shape:

```
modules/orders/
├── orders.routes.ts       # route declarations + middleware chain only
├── orders.controller.ts   # HTTP in/out: parse (zod), withTenant(), call service, shape response. NO business logic.
├── orders.service.ts      # ALL business logic. Takes `tx`. No req/res. Throws AppError. Testable in isolation.
├── orders.tools.ts        # tools-registry entries for this module's owner actions (key, schema, side effect, handler)
├── orders.events.ts       # event types this module writes + their payload zod schemas
└── orders.test.ts
```

- Controllers never touch `db`. Services never import Express types. Services receive `tx` (a tenant-bound transaction) as the first argument.
- Cross-module calls go **service → service**, passing the same `tx`.
- Side effects are decoupled through **`app.events`** (the transactional outbox): a service writes the event row inside its transaction; workers consume events and run automations, feature updates, WhatsApp sends, Socket.IO emits. Handlers are idempotent on `events.idempotency_key` and never crash the writer.
- The `tools` registry (`*.tools.ts`) is built from the same zod schemas as the routes and seeded into `app.tools` at boot. The owner bot, automations and the UI all call `runTool(key, ctx, input)` — one code path, one audit trail (`tool_executions`).

## 4. Multi-tenancy (the load-bearing wall)

- Shared tables; every tenant-owned row carries `vendor_id` + `outlet_id`. **Postgres Row-Level Security** on every table that has a `vendor_id` column (policy generated by migration `10_rls_grants.sql`; a new table gets it automatically).
- **`tenantContext` middleware** resolves `{ vendorId, outletIds }` from the JWT (never from params/body/query) into `req.tenant`.
- **`withTenant(req.tenant, tx => …)`** opens a transaction as role `regulars_app` and sets `app.vendor_id` (`SET LOCAL`). Every vendor-scoped query runs inside it. The app never writes `WHERE vendor_id` itself — RLS does.
- Customer-facing routes set `app.customer_id` after OTP; `customers` (global table) is readable only for the logged-in customer or through the vendor's own `customer_profiles` row.
- Workers use `asWorker()` (role `regulars_worker`, BYPASSRLS) and must filter by `vendor_id` explicitly; allowed only under `jobs/` (ESLint rule).
- Cross-tenant access is a **test-enforced invariant**: the tenant-leak matrix is generated from `information_schema.columns WHERE column_name = 'vendor_id'`, so a new table can't ship without joining it (`06-security-checklist.md` §4).

## 5. Request lifecycle (canonical)

```
request
 → requestId middleware (uuid, attached to logs)
 → helmet / cors (allowlist)
 → rate limiter (per route class — see 06 §6)
 → body parse (json, 100kb limit)
 → auth middleware (route-dependent)
 → tenantContext (vendor routes) / customerContext (customer routes)
 → validate(zodSchema) — parses body/params/query; 422 on failure
 → controller → withTenant(tx) → service → drizzle
 → success: res.json(envelope)   |   throw AppError
 → central errorHandler (LAST middleware): maps AppError → envelope, PG 23505 on idempotency key → replay,
   unknown errors → 500 + logged with requestId, never leak stack/internals
```

## 6. AuthN/AuthZ

- **Customers:** phone + OTP (6-digit, 5-min TTL, hashed in Redis, max 3 verify attempts, resend cooldown 60 s, max 5 OTPs/phone/hour). OTP delivered via WhatsApp authentication template (SMS provider interface stubbed). First-timer: name + consent checkbox (DPDP notice version recorded).
- **Owners & super_admin:** email + password (argon2id), optional 2FA later. Staff logins v1.1.
- Access JWT (15 min) carries `{ sub, role, vendorId, outletIds? }`, RS256. Refresh token: opaque, rotating, hashed in `refresh_tokens` with device info; reuse of a rotated token revokes the family.
- Frontends keep the access token in memory only; refresh via httpOnly `SameSite=Strict` cookie.
- RBAC: `authorize(...roles)` middleware + RLS for tenant ownership + service-level checks for object ownership within the tenant.
- Socket.IO: JWT at handshake; owner sockets join `vendor:{vendorId}`; customer sockets join `session:{token}` after ownership check.
- **Owner bot identity:** inbound WhatsApp from a number matching `users.phone` → owner conversation → agent session bound to that user and vendor. Answers only from data the `tools` registry can read for that tenant.

## 7. Payments (money never touches us)

```
customer taps Pay (after acceptance for tables; before for counter)
  → billing.service creates payments row (status created) + PaymentProvider.createRequest(outlet gateway creds)
  → customer pays on gateway page/UPI intent → gateway webhook → webhooks/{provider}
  → signature verify → webhook_dedupe → webhook_events (raw) → job → payments.status captured → bills.paid_amount += → events bill_paid
  → Socket.IO table:updated / round:status; e-bill queued
```

- Outlet-level gateway credentials (vault refs) — each restaurant is merchant of record; we hold no funds and issue no refunds. Refunds are three owner-chosen modes recorded as `payments(kind='refund')`: back-to-source via the gateway adapter, cash at counter, adjust-replace.
- Cash / UPI / card at counter are recorded by staff; a bill can carry several payment rows (day-close sums payments, not bills).
- Pay-at-checkout outlets never create a gateway request until settle.

## 8. WhatsApp pipeline (never call Meta synchronously from a request)

```
event (bill_paid, order_accepted …) / campaign / trigger / OTP
  → NotificationService.send(message)         # channel-agnostic interface
  → INSERT messages (status queued) [+ message_dedupe]
  → BullMQ 'whatsapp' queue
  → worker: consent check → STOP check → weekly cap → vendor quota → 24h-window check (utility rides the window)
            → template render → Cloud API call
      success  → messages.sent_at (delivered/read via webhook)
      4xx      → failed_permanent (no retry); 131049 → skipped, reason meta_cap_131049
      5xx/429  → retry with backoff (5 attempts) → failed_retryable → DLQ
  → webhook: statuses → messages timeline; inbound → conversations (window opens 24 h) → STOP handling / owner bot / customer auto-reply
```

- Consent + caps are checked **in the worker at send time**.
- Crons (BullMQ repeatable, IST): birthday scan 08:00, segment recompute 03:00, win-back 03:30, dead-hour detection 04:00, morning briefing 08:00 (owner's chosen time), order auto-expiry every minute, overnight-tab audit 05:00. All idempotent via `message_dedupe` / `automation_runs.idempotency_key`.
- **Channel model:** v1 = one platform WABA; `whatsapp_channels` supports per-vendor WABA (v1.5 Tech Provider). Inbound webhooks route by `phone_number_id`.
- Every send records `billable` / `in_window` / `pricePaise` for the cost report (1 Oct 2026 rate-card change).

## 9. AI layer (v1 = read-only, zero-data features)

- `tools` registry = every owner action (`orders.accept`, `reports.revenue`, `menu.setAvailability` …) with a JSON schema from the route's zod, `side_effect` (read/write/irreversible) and `requires_confirmation`. v1 exposes **read** tools to the bot.
- Owner bot: WhatsApp reply → `agent_sessions` (short-term memory) → `agent_runs` (one per turn; steps = LLM / tool / RAG / guard) → answer. Data scope = the owner's tenant only, enforced twice (RLS + `ToolExecutionContext.tenant`).
- RAG: `documents` (menu, outlet profile, FAQ, briefing, insights) chunked into `document_chunks` with pgvector HNSW; mandatory tenant filter.
- Menu photo extraction: `menu_imports` + `menu_import_rows` (original vs accepted = training pairs).
- Briefing: `briefings` row built from yesterday's `events`/bills, rendered by template (LLM optional), sent as a WhatsApp template; the reply thread is the bot.
- Feedback loop: `ml.ai_feedback` (thumbs, corrections, insight acted/dismissed, funnel drop-offs), `training_eligible` per row.
- v1.5 writes: same tools with `requires_confirmation` → `tool_executions.status = awaiting_confirmation` → owner replies YES on WhatsApp (one-sentence actions) or confirms in-app (anything with a preview). Irreversible tools are never automatic.

## 10. Real-time strategy

- After DB commit, the worker (event consumer) emits `order:new`, `order:status`, `table:service_call`, `table:updated`, `board:updated` to `vendor:{vendorId}`; `round:status`, `table:updated`, `payment:status` to `session:{token}`.
- Socket emit failures never fail the HTTP request. Both frontends poll every 30 s as reconciliation — the socket is latency, not truth.

## 11. Frontend architecture (all React apps)

```
src/
├── api/          # ONE axios instance + generated per-module API functions; zod-parse responses
├── components/   # dumb/presentational, no data fetching
├── features/     # feature folders: components + hooks + local state per feature
├── hooks/        # shared hooks
├── routes/
├── stores/       # zustand slices (cart, ui) — server data stays in TanStack Query
└── lib/          # utils, i18n, constants re-exported from packages/shared
```

- Owner side: **desktop**, left sidebar Orders / Tables / Menu / Reports / Settings; screens for reading, **sheets** for doing, one primary button per screen, status by colour + position. Table badge is the visual spine.
- Customer side: **mobile PWA**, no app. Cart persists to localStorage with schema-versioned zod parse. Cart primary button = **"Place order"** (payment prompt arrives after acceptance). Add-to-home-screen prompt after first order. Bundle budget ≤ 200 kB gzipped initial JS.
- i18n: all strings through i18next from day one; `en` shipped, `hi`/Hinglish later.

## 12. Observability & ops

- pino structured logs with `requestId`, `vendorId`, `userId`; PII redaction (06 §8).
- `/healthz`, `/readyz` (postgres + redis ping). Graceful shutdown drains in-flight requests and jobs.
- Sentry on api + frontends from day one. Alerts: 5xx spike, DLQ growth, webhook signature failures, replication-slot lag, DEFAULT partition non-empty, OTP budget breach.
- Backups: Supabase PITR; Redis is rebuildable state only. Weekly restore rehearsal on staging.

## 13. Environments & config

- `local` (docker-compose: postgres 16 + pgvector, redis), `staging` (Supabase branch or second project), `production`.
- All config via env vars parsed once by a zod schema in `config/env.ts`; the app refuses to start on missing config. `DATABASE_URL` (pooler, transaction mode) for runtime; `DATABASE_DIRECT_URL` for migrations, `drizzle-kit pull`, and the CDC slot.
- Secrets never in the repo. Gateway/WABA credentials are vault references stored in `*_ref` columns.
