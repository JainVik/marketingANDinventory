# 03 — Database Schema (PostgreSQL, v1)

*Field-level schema for v1, architected for v1.5 (owner bot writes, churn ML, per-vendor WABA), v2 (hotels, inventory, multi-outlet) and the ML pipeline. 5 Sep 2026. Supersedes the MongoDB version.*

**Decisions this doc is built on:** PostgreSQL on **Supabase** (PG 16, pgvector, pg_cron, pg_partman available) · **shared tables + Row-Level Security** for tenant isolation · **SQL DDL is the source of truth, Drizzle is generated from it** (`drizzle-kit pull`) — my assumption since the format question went unanswered; swap to Prisma is a one-command introspect, nothing here changes.

**Files:** `db/migrations/0001_init.sql` (the 11 sections below, concatenated — loads clean on PG 16; `db/seed/smoke.sql` proves RLS isolation, idempotency, guarded transitions, partitions, append-only guards). ERD: `docs/03-schema-atlas.html`.

## 0. Conventions (binding)

| Rule | Detail |
|---|---|
| Schemas | `pii` (**identity**: phone, name, birthday, consent ledger, customer devices & tokens), `app` (business), `ml` (feature store / training), `ops` (counters, watermarks, partition mgmt). |
| Tenant keys | `vendor_id` (tenant) + `outlet_id` (branch) on every tenant-owned row. Both set by the API from the JWT: `SET LOCAL app.vendor_id = …` per transaction. **RLS policy on every table with a `vendor_id` column**, generated by one loop — a new table gets the policy for free. |
| Global tables | `pii.customers`, `tools`, `agents`, `agent_prompts`, `ops.*`, platform rows with `vendor_id IS NULL` in `whatsapp_channels`, `message_templates`, `documents`. |
| **PII boundary** | Customer identity lives in schema `pii` and **`regulars_app` has no table grant on it**. The API reaches it only through `pii.customer_public` (a view with no phone and no name) and two `SECURITY DEFINER` functions, `pii.reveal_identity()` / `pii.reveal_phone()`, which refuse unless the calling vendor has a `customer_profiles` row with `first_order_at IS NOT NULL`. A stolen `regulars_app` credential yields orders and totals, never a phone book. Exceptions, both deliberate: `bills.customer_phone` (GST invoices must carry it, and the customer ordered there by definition) and `conversations`/`messages` (the WhatsApp ledger — phone column revoked from `regulars_app` by column-level grant; the worker sends, the owner UI sees `98•••••210`). |
| **Identity vs. visibility** | The identity row is created at **OTP**; it is global (one per human, every outlet). The vendor's view of that human is created at **first order** — `customer_profiles.revealed_at` and the `display_name` snapshot are written in the same transaction as the first `order_placed`. Before that a vendor sees counts, never a person. |
| IDs | `uuid` (`gen_random_uuid()`) for entities other tables reference and the client sees. `bigint` sequence for append-only / high-volume rows (`events`, `messages`, `order_lines`, `audit_logs`, …). Public tokens (`tables.qr_token`, `dining_sessions.token`) = 12-char base62. |
| Money | `app.paise` domain = `bigint CHECK (>= 0)`. Never numeric/float. Sign lives in `kind`/`direction` columns. |
| Time | `timestamptz` (UTC). IST denormalisation `local_date`, `weekday`, `day_part` (`morning` 06–10, `noon` 11–15, `evening` 16–20, `night` 21–05), `hour_local` — set by one trigger `app.set_local_time('<ts column>')` on orders / bills / payments / sessions / events / messages / agent_runs / tool_executions. |
| State | State changes are **timestamp columns** (`accepted_at`, `ready_at`, …); `status` is a derived convenience column changed only by guarded `UPDATE … WHERE status = $expected` (rowcount 0 → 409). CHECK constraints tie status ↔ timestamps where cheap. |
| History | Never mutated. Prices → `menu_item_revisions`; orders snapshot names/prices into `order_lines`; bills snapshot seller + customer. |
| Deletes | Soft: `deleted_at`. Partial indexes `WHERE deleted_at IS NULL`. `regulars_app` has **no DELETE grant** except session-scoped tables. Hard delete only in the DPDP erasure job (§4.7). |
| Append-only | Enforced by `BEFORE UPDATE OR DELETE` trigger `app.forbid_change()`: `events`, `audit_logs`, `coupon_redemptions`, `revenue_attributions`, `customer_consent_events`; `payments` allows status-field updates only (column-guard trigger). |
| Enums | Postgres `ENUM` types in schema `app` (65). Extend with `ALTER TYPE … ADD VALUE` (transactional since PG 12; new value usable next transaction). Never rename. |
| Flexible payloads | `jsonb` only where the shape is genuinely open or provider-owned: `raw` (webhooks), `payload` (events), `input`/`output` (tools), `custom_attributes`, `attributes`, `definition` (segments), `graph` (automations), `snapshot` (revisions/briefings), `components` (Meta templates). Everything the app filters or joins on is a typed column. |
| Versioning | `schema_version smallint` on rows that will migrate (orders, bills, payments, sessions, profiles, messages, events, agent_runs, tool_executions). |
| Partitioning | Native `RANGE` monthly on `events`, `messages`, `webhook_events`, `audit_logs`, `browse_sessions`, `browse_events`, `ml.customer_features`. `ops.ensure_month_partitions()` + pg_cron keeps 3 months ahead; DEFAULT partition catches strays. |
| Vectors | pgvector `vector(1536)` + HNSW cosine on `document_chunks`. |

Build tags: **[v1]** build now · **[v1-field]** column only, feature later · **[v1.5]** · **[v2]** · **[reserve]** name reserved, no table created.

### 1.2 Domain wiring — how the layers stay decoupled

```
core modules ──INSERT in same txn──▶ app.events (append-only outbox, partitioned)
                                         │
                                         ├──▶ automations (trigger rules) ──▶ tools (action registry) ──▶ core services
                                         ├──▶ ml.customer_features / ml.outlet_features (feature jobs, pg_cron + worker)
                                         ├──▶ watermark pull ──▶ parquet lake (S3 / Supabase Storage)   [CDC-lite]
                                         └──▶ insights / briefings ──▶ agent_sessions ──▶ owner bot (reads via tools)

mutable tables (orders, bills, customer_profiles, menu_items, outlets) ──logical replication (pgoutput)──▶ lake  [CDC-full]
```

- Core tables never learn about AI. AI reads `events`, `ml.*`, `insights` and calls `tools`.
- Every owner action = one row in `tools` + one service function. Order desk UI, owner bot (v1 read / v1.5 write), automations and future MCP all call the same registry.
- Adding a module = new tables + new `app.event_type` values + new `tools` rows. Zero `ALTER` on `orders` / `bills` / `customers`.
- RLS is generated from the presence of a `vendor_id` column — the isolation wall follows every new table automatically.

-- IST denormalisation: local_date / weekday / day_part / hour_local from a timestamptz column named by TG_ARGV[0]
CREATE OR REPLACE FUNCTION app.set_local_time() RETURNS trigger LANGUAGE plpgsql AS $$
DECLARE ts timestamptz; lt timestamp; h int;
BEGIN
  EXECUTE format('SELECT ($1).%I', TG_ARGV[0]) INTO ts USING NEW;
  IF ts IS NULL THEN ts := now(); END IF;
  lt := ts AT TIME ZONE 'Asia/Kolkata';
  h  := extract(hour FROM lt);
  NEW.local_date := lt::date;
  NEW.weekday    := extract(dow FROM lt);
  NEW.hour_local := h;
  NEW.day_part   := CASE WHEN h BETWEEN 6 AND 10 THEN 'morning' WHEN h BETWEEN 11 AND 15 THEN 'noon'
                         WHEN h BETWEEN 16 AND 20 THEN 'evening' ELSE 'night' END::app.day_part;
  RETURN NEW;
END $$;

  SELECT CASE WHEN extract(month FROM (ts AT TIME ZONE 'Asia/Kolkata')) >= 4
              THEN extract(year FROM (ts AT TIME ZONE 'Asia/Kolkata'))::int || '-' || lpad(((extract(year FROM (ts AT TIME ZONE 'Asia/Kolkata'))::int + 1) % 100)::text, 2, '0')
              ELSE (extract(year FROM (ts AT TIME ZONE 'Asia/Kolkata'))::int - 1) || '-' || lpad((extract(year FROM (ts AT TIME ZONE 'Asia/Kolkata'))::int % 100)::text, 2, '0') END $$;

BEGIN
  IF NEW.amount <> OLD.amount OR NEW.kind <> OLD.kind OR NEW.mode <> OLD.mode OR NEW.bill_id <> OLD.bill_id OR NEW.idempotency_key <> OLD.idempotency_key THEN
    RAISE EXCEPTION 'payments is append-only except status fields';

  RETURN NEW;
END $$;

-- Creates monthly partitions [this month .. +months_ahead] for a RANGE(timestamptz) table. Called by pg_cron weekly.
CREATE OR REPLACE FUNCTION ops.ensure_month_partitions(p_schema text, p_table text, p_months_ahead int DEFAULT 3)
RETURNS void LANGUAGE plpgsql AS $$
DECLARE d date := date_trunc('month', now() AT TIME ZONE 'Asia/Kolkata')::date; i int; part text;
BEGIN
  FOR i IN 0..p_months_ahead LOOP
    part := format('%s_%s', p_table, to_char(d + (i || ' months')::interval, 'YYYY_MM'));
    IF NOT EXISTS (SELECT 1 FROM pg_class c JOIN pg_namespace n ON n.oid = c.relnamespace WHERE n.nspname = p_schema AND c.relname = part) THEN
      EXECUTE format('CREATE TABLE %I.%I PARTITION OF %I.%I FOR VALUES FROM (%L) TO (%L)',
                     p_schema, part, p_schema, p_table,
                     (d + (i || ' months')::interval)::timestamptz, (d + ((i+1) || ' months')::interval)::timestamptz);
    END IF;
  END LOOP;
END $$;

-- initial partitions (also run this from the migration; pg_cron keeps it rolling)

-- ---------- updated_at on every table that has the column --------------
DO $$
DECLARE r record;
BEGIN
  FOR r IN SELECT n.nspname, c.relname FROM pg_attribute a
           JOIN pg_class c ON c.oid = a.attrelid JOIN pg_namespace n ON n.oid = c.relnamespace
           WHERE a.attname = 'updated_at' AND NOT a.attisdropped AND c.relkind IN ('r','p') AND n.nspname IN ('app','ml','ops')
  LOOP
    EXECUTE format('CREATE TRIGGER %I BEFORE UPDATE ON %I.%I FOR EACH ROW EXECUTE FUNCTION app.touch_updated_at()',
                   r.relname || '_touch', r.nspname, r.relname);
  END LOOP;
END $$;

-- ---------- Row-Level Security ---------------------------------------
-- Model: shared tables, vendor_id on every tenant row. API role regulars_app runs every transaction as:
--   SET LOCAL ROLE regulars_app; SET LOCAL app.vendor_id = '<uuid from JWT>'; [SET LOCAL app.outlet_ids = 'a,b']
-- Workers/ML use BYPASSRLS roles and pass vendor_id explicitly in SQL.
-- Policy shape: rows whose vendor_id is the current tenant; platform rows (vendor_id IS NULL) are readable by everyone.
DO $$
DECLARE r record; nullable boolean;
BEGIN
  FOR r IN SELECT n.nspname, c.relname, a.attnotnull FROM pg_attribute a
           JOIN pg_class c ON c.oid = a.attrelid JOIN pg_namespace n ON n.oid = c.relnamespace
           WHERE a.attname = 'vendor_id' AND NOT a.attisdropped AND c.relkind IN ('r','p') AND n.nspname IN ('app','ml')
             AND c.relname NOT LIKE '%\_default' AND c.relname !~ '_\d{4}_\d{2}$'          -- partitions inherit
  LOOP
    EXECUTE format('ALTER TABLE %I.%I ENABLE ROW LEVEL SECURITY', r.nspname, r.relname);
    EXECUTE format('ALTER TABLE %I.%I FORCE ROW LEVEL SECURITY',  r.nspname, r.relname);   -- even the table owner obeys
    IF r.attnotnull THEN
      EXECUTE format('CREATE POLICY tenant_isolation ON %I.%I FOR ALL TO regulars_app USING (vendor_id = app.current_vendor_id()) WITH CHECK (vendor_id = app.current_vendor_id())', r.nspname, r.relname);
    ELSE
      EXECUTE format('CREATE POLICY tenant_isolation ON %I.%I FOR ALL TO regulars_app USING (vendor_id IS NULL OR vendor_id = app.current_vendor_id()) WITH CHECK (vendor_id = app.current_vendor_id())', r.nspname, r.relname);
    END IF;
  END LOOP;
END $$;

### 2b.1 Tenant transaction wrapper (the one piece of code that makes RLS real)

```ts
// db/client.ts
import { drizzle } from 'drizzle-orm/node-postgres';
import { Pool } from 'pg';
import { sql } from 'drizzle-orm';
import * as schema from './schema';

const pool = new Pool({ connectionString: env.DATABASE_URL, max: 20 });   // Supabase pooler (transaction mode) → keep SET LOCAL, never SET
export const db = drizzle(pool, { schema });

export type Tenant = { vendorId: string; outletIds?: string[]; customerId?: string };

/** Every vendor-scoped request runs inside this. RLS does the filtering; the app never appends WHERE vendor_id itself. */
export async function withTenant<T>(t: Tenant, fn: (tx: typeof db) => Promise<T>): Promise<T> {
  return db.transaction(async (tx) => {
    await tx.execute(sql`SET LOCAL ROLE regulars_app`);
    await tx.execute(sql`SELECT set_config('app.vendor_id', ${t.vendorId}, true)`);
    if (t.outletIds?.length) await tx.execute(sql`SELECT set_config('app.outlet_ids', ${t.outletIds.join(',')}, true)`);
    if (t.customerId)        await tx.execute(sql`SELECT set_config('app.customer_id', ${t.customerId}, true)`);
    return fn(tx as unknown as typeof db);
  });
}

/** Workers / crons: BYPASSRLS role, vendor passed explicitly in every query (lint rule: no bare selects on tenant tables). */
export async function asWorker<T>(fn: (tx: typeof db) => Promise<T>) {
  return db.transaction(async (tx) => { await tx.execute(sql`SET LOCAL ROLE regulars_worker`); return fn(tx as unknown as typeof db); });
}
```

Middleware: `tenantContext` resolves `{ vendorId, outletIds }` from the JWT → `req.tenant`; controllers call `withTenant(req.tenant, tx => service.fn(tx, …))`. A service that receives a `tx` cannot escape the tenant — the lint rule from the Mongo era (`scopedModel`) becomes "services take `tx`, never import `db`".

export async function searchChunks(tx: Db, t: Tenant, embedding: number[], opts: { k?: number; kinds?: DocKind[]; language?: Language }) {
  const k = Math.min(opts.k ?? 6, 8);
  await tx.execute(sql`SET LOCAL hnsw.ef_search = 80`);                          // recall for filtered scans
  await tx.execute(sql`SET LOCAL hnsw.iterative_scan = relaxed_order`);          // pgvector ≥ 0.8; keeps scanning until k rows pass the WHERE
  return tx.execute(sql`
    SELECT id, document_id, text, kind, 1 - (embedding <=> ${toVector(embedding)}) AS score
    FROM app.document_chunks
    WHERE (vendor_id = ${t.vendorId} OR vendor_id IS NULL)                        -- RLS enforces this too; explicit for the planner
      ${opts.kinds ? sql`AND kind = ANY(${opts.kinds})` : sql``}
      ${opts.language ? sql`AND language = ${opts.language}` : sql``}
    ORDER BY embedding <=> ${toVector(embedding)}
    LIMIT ${k}`);
}

### 3.4 Browse telemetry beacon (item 68)

The customer PWA batches interactions and flushes them on a 10-second timer, on `visibilitychange`, and via `navigator.sendBeacon` on unload. **The beacon is not the outbox**: it writes `browse_sessions` / `browse_events` on its own connection, outside any order transaction, and a failure there is logged and dropped — it must never surface to the customer or block a placement.

```jsonc
// POST /public/v/{slug}/t/{token}/telemetry     (no auth; visitorId is the only identity)
{
  "visitorId": "uuid",              // issued by the server on first scan, kept in localStorage
  "browseSessionId": "uuid",        // issued with it, one per visit
  "flushedAt": "2026-09-09T14:22:03Z",
  "events": [                       // max 50 per flush, max 200 per browse session
    { "seq": 1, "kind": "menu_viewed",       "at": "…", "scrollPct": 0 },
    { "seq": 2, "kind": "category_viewed",   "at": "…", "menuCategoryId": "uuid" },
    { "seq": 3, "kind": "item_viewed",       "at": "…", "menuItemId": "uuid", "dwellMs": 2400 },
    { "seq": 4, "kind": "item_sheet_opened", "at": "…", "menuItemId": "uuid" },
    { "seq": 5, "kind": "left",              "at": "…", "scrollPct": 75 }
  ]
}
```

Rules, all testable:

- `seq` is client-monotonic per browse session, and the ingest writes `occurred_at` from the event's `at` — **never `now()`**. The unique key is `(browse_session_id, seq, occurred_at)` (a partitioned table must include its partition column), so a replay that resends the identical `at` collides with 23505 and is ignored. An ingest that defaults the timestamp would double-count every retry: that is the bug this rule exists to prevent. 🧪
- `at` is clamped server-side to `[flushedAt - 6h, flushedAt + 1m]`; anything outside is rewritten to `flushedAt`, so a wrong client clock cannot scatter rows across partitions.
- `item_viewed` is emitted once per item per visit, only after **1 000 ms** in the viewport. `scroll_pct` is quantised to 25/50/75/100. Neither is a continuous stream.
- Rate limit: 12 flushes/min per `visitorId`, 240/min per outlet. Over the cap the beacon 202s and drops — never 4xx into the customer's console.
- The payload carries **no PII and no free text**: no phone, no name, no search terms in v1 (`search_performed` records that a search happened and the result count, not the string).
- `is_practice` is copied from the table, so practice traffic never enters an owner's numbers.
- On OTP verify, the identity service sets `visitors.customer_id`, backfills `browse_sessions.customer_id` for that visitor's **last 24 hours**, and writes one `visitor_identified` event. Older anonymous history stays anonymous.

## Step 4 — Performance, Indexing & Scaling Blueprint (Postgres / Supabase)

### 4.1 Index rules

1. Indexes live in the SQL migrations only (they are, above). `drizzle-kit pull` mirrors them; nobody creates indexes from TS.
2. Tenant-first: every index on a tenant table starts `(vendor_id, outlet_id?, …)` — matches the RLS predicate so the planner uses it for the policy filter too.
3. Unique = business invariant: `qr_token`, `dining_sessions.token`, `(outlet_id, financial_year, invoice_seq)`, `(outlet_id, idempotency_key)` ×2, `(session_id, round_number)`, one-active-session-per-table (partial), `(vendor_id, customer_id)`, `(vendor_id, code)`, `(outlet_id, local_date)` ×3, `(campaign_id, profile_id)`, `message_dedupe.dedupe_key`, `webhook_dedupe (source, event_id)`, `tool_executions.idempotency_key`, `insights.dedupe_key`.
4. Partial indexes for job scans: `orders WHERE status='placed'`, `messages WHERE status='failed_retryable'`, `webhook_events WHERE proc_status IN ('received','failed')`, `tool_executions WHERE status='awaiting_confirmation'`, `dining_sessions WHERE status='active'`, `menu_items WHERE auto_restore <> 'never'`.
5. Soft-delete aware: hot indexes carry `WHERE deleted_at IS NULL`.
6. GIN: `customer_profiles.tags` (btree_gin with vendor_id), `custom_attributes` (jsonb_path_ops), `menu_items.tags`, `events.payload` (jsonb_path_ops — drop if write amplification shows). Trigram GIN on `customer_profiles.display_name`, `menu_items.name` for search.
7. Never index a `jsonb` key that the app filters on regularly — promote it to a typed column (that is the rule that produced the typed `outlets.*` settings columns).
8. `EXPLAIN (ANALYZE, BUFFERS)` gate in CI: the 10 hottest queries against seed data; fail on `Seq Scan` over a tenant table > 10k rows.

### 4.2 Index catalogue by type

| Type | Where | Why |
|---|---|---|
| B-tree composite (tenant-first) | all tenant tables | every dashboard query + RLS predicate |
| Unique (incl. partial unique) | 16 invariants in §4.1.3 | correctness under concurrency |
| Partial | jobs / workers | tiny, always cached |
| GIN (btree_gin, jsonb_path_ops, pg_trgm) | tags, custom attrs, names, event payload | filters and search |
| HNSW (pgvector) | `document_chunks.embedding` | RAG |
| Covering (`INCLUDE`) | add later for Regulars Board: `dining_session_customers (session_id) INCLUDE (badge, visit_count)` | index-only scans |
| BRIN | `events (occurred_at)`, `messages (created_at)` per partition once partitions exceed ~10 GB | cheap range scans on append-only |

### 4.3 Vector index

```sql
CREATE INDEX document_chunks_embedding_hnsw ON app.document_chunks USING hnsw (embedding vector_cosine_ops) WITH (m = 16, ef_construction = 64);
-- query-time: SET LOCAL hnsw.ef_search = 80; SET LOCAL hnsw.iterative_scan = relaxed_order;   (pgvector 0.8+, on Supabase)
```

- HNSW is not partitionable per tenant; the `WHERE vendor_id = …` pre-filter + iterative scan is the correct pattern up to ~5M chunks. Past that: partition `document_chunks` by `vendor_id` hash (16 partitions, one HNSW each).
- One dimension per column. A 768-d model → add `embedding_768 vector(768)` + its own index; `embedding_version` selects. Never mix dims in one column.
- Re-embed = insert new chunks with new `embedding_version`, flip `agents.rag_kinds`/version, delete old after 24 h.
- `halfvec(1536)` (2 bytes/dim) halves index size at ~no recall cost — switch when index > RAM.
- Build with `SET maintenance_work_mem = '2GB'` on Supabase (compute add-on) or build concurrently.

### 4.4 Volume model & partitioning

Assumption at 12 months: 500 outlets × 120 orders/day.

| Table | Rows/day | Rows/year | Row size | Growth/yr | Strategy |
|---|---|---|---|---|---|
| `orders` + `order_lines` | 60k + 200k | 22M + 73M | 0.5 KB + 0.2 KB | ~25 GB | plain; BRIN on `placed_at` at 50M rows |
| `events` | ~600k | 220M | ~0.5 KB | ~110 GB | monthly RANGE partitions |
| `messages` | ~150k | 55M | ~1 KB | ~55 GB | monthly RANGE partitions |
| `webhook_events` | ~300k | 110M | ~2 KB (raw) | ~220 GB | monthly partitions, **30-day retention** (drop partition) |
| `ml.customer_features` | ~100k | 36M | ~1 KB | ~36 GB | monthly partitions |
| `audit_logs` | ~50k | 18M | ~1 KB | ~18 GB | monthly partitions |
| `browse_sessions` | ~250k | 90M | ~0.4 KB | ~36 GB | monthly partitions, **400-day retention** |
| `browse_events` | ~2.5M | 900M | ~0.15 KB | ~135 GB | monthly partitions, **90-day retention** (drop partition) |
| `agent_runs` + `steps` + `tool_executions` | ~20k | 7M | ~3 KB | ~20 GB | plain; partition at year 2 |

**Partition mechanics (all seven tables):**

- `PARTITION BY RANGE (<ts>)`, monthly, named `events_2026_09`. `ops.ensure_month_partitions(schema, table, 3)` creates 3 months ahead; pg_cron runs it weekly: `SELECT cron.schedule('partitions', '0 3 * * 1', $$SELECT ops.ensure_month_partitions('app','events',3); …$$);`. DEFAULT partition catches strays; alert if it is non-empty.
- Supabase alternative: `pg_partman` (`partman.create_parent('app.events','occurred_at','native','monthly', p_premake := 3)`) — same result, one dependency more. Either.
- PK = `(id, ts)`; other tables store the `id` **without FK** (Postgres cannot FK to a partitioned table without the partition key). The soft links are in `relations.ts` and the ERD (dashed).
- Global uniqueness that must survive across partitions lives in small side tables: `message_dedupe`, `webhook_dedupe`.
- Retention: `browse_events` → drop the partition after 90 days (the insight lives in the `browse_sessions` summary, which is kept 400 days, then archived like `events`). `webhook_events` → `DROP TABLE app.webhook_events_2026_06` after 30 days (raw already processed; the normalised rows live in `messages`/`payments`). `events`, `messages`, `audit_logs`: **never dropped** — after 13 months `ALTER TABLE … DETACH PARTITION`, `pg_dump` the partition to Parquet (`pg_parquet` / DuckDB `postgres_scanner`), upload to Supabase Storage / S3, then drop. Orders/bills/payments stay hot for 8 years (GST).
- Queries always carry the time predicate (`occurred_at >= …`) so partition pruning works; the `events_id_ix` exists only for watermark pulls.

**Sharding:** none. A single Supabase Postgres (8–16 vCPU) carries this volume for years. Read replicas for reports/ML (Supabase read replicas or `regulars_ml` on a replica) before any horizontal split.

### 4.5 Write-path rules

- Order placement = one transaction: `dining_sessions` (row lock) → `menu_items` (guarded stock UPDATE) → `orders` + `order_lines` → session totals → `events` insert. ≈ 6 statements, < 15 ms.
- Webhook endpoint: verify signature → `INSERT INTO webhook_dedupe … ON CONFLICT DO NOTHING RETURNING` → if inserted, `INSERT webhook_events` → `202` in < 30 ms → BullMQ job processes → writes `messages`/`payments` → updates `proc_status`.
- Workers batch-insert `events`/`messages` (`INSERT … VALUES (…),(…)` 200/batch, `ON CONFLICT DO NOTHING` on the idempotency index).
- Denormalised counters (`customer_profiles.*`, `menu_items.orders_30d`, `outlets.customer_count`, `campaigns.n_*`) updated only by idempotent event handlers keyed on `events.idempotency_key` — never by request handlers.
- Supabase pooler runs in **transaction mode**: use `SET LOCAL` only, no prepared-statement names, no `LISTEN`. Direct connection for migrations and the CDC slot.
- `synchronous_commit = on` (default) for money tables; workers may `SET LOCAL synchronous_commit = off` for `events` batch inserts.

### 4.6 CDC — two rails into the ML lake

> **PII allowlist.** Schema `pii` is **never** replicated to the lake. The publication is defined over `app` and `ml` only, and CI fails if a `pii.*` table appears in `pg_publication_tables`. 🧪 `browse_sessions` and `browse_events` export in full (they hold no PII by construction); `visitors` exports without `ua_family`.

```
                       ┌── watermark pull (SELECT … WHERE id > $last ORDER BY id LIMIT 5000) ──▶ parquet ──┐
append-only tables ────┤   events, messages, audit_logs, tool_executions, revenue_attributions             │
                       └── ops.etl_watermarks stores last_id per consumer                                    │
                                                                                                             ├─▶ s3://regulars-lake/{table}/local_date=…/part-*.parquet
mutable tables ────────── logical replication slot (pgoutput, publication regulars_cdc) ──▶ Debezium/       │       └─▶ DuckDB / Athena / BigQuery later
  orders, order_lines, bills, payments, dining_sessions,                                    pg-logical-stream │
  customer_profiles, menu_items, outlets, campaigns, campaign_recipients                  ──▶ change rows ────┘
```

Setup:

1. **Publication + slot** (direct connection, once): `CREATE PUBLICATION regulars_cdc FOR TABLE app.orders, app.order_lines, app.bills, app.payments, app.dining_sessions, app.customer_profiles, app.menu_items, app.outlets, app.campaigns, app.campaign_recipients;` and `ALTER TABLE app.orders REPLICA IDENTITY FULL;` (same for the others) so updates carry the full old row. `wal_level = logical` is on by default on Supabase. Consumer: Debezium (Postgres connector) or a 200-line Node consumer on `pg-logical-replication`; the lag is a Prometheus gauge from `pg_replication_slots.confirmed_flush_lsn`.
2. **Watermark rail** for append-only tables: cheaper and exactly-once by construction (id is monotonic per partition set; `ops.etl_watermarks` commits `last_id` after the parquet file is durable). Runs every 5 min in the worker.
3. **Exactly-once at the sink**: parquet rows keyed `(table, id, lsn|updated_at)`; sink dedupes on load.
4. **PII policy at the CDC boundary**: consumer strips `phone`, `name`, `email`, `content_text`, `raw`, `customer_*` snapshot columns before writing. Opaque ids stay. `messages.content_text` and `agent_runs.input_text` reach the lake **only** for rows where `ml.ai_feedback.training_eligible = true` (joined at export). Hard rule, enforced by a column allowlist per table in the consumer config.
5. **Lake layout**: `{table}/local_date=YYYY-MM-DD/`, `schema_version` column for evolution; `events` additionally `event_type=…`.
6. **Backfill**: `etl backfill --table events --from 2026-09-01` reads by `id` range, same sink dedupe.
7. **Feature jobs**: training reads the lake; serving reads `ml.customer_features` latest row (or the copy in `customer_profiles`). Same `pipeline_version` in both → no train/serve skew.
8. **Supabase-native option**: Supabase "Replication" (ETL to BigQuery/Iceberg, currently beta) replaces step 1 if it GA's — the publication is the same either way.
9. **Alarms**: replication slot lag > 1 GB, `etl_watermarks.lag_seconds` > 300, DEFAULT partition row count > 0.

### 4.7 Tenancy, isolation & DPDP

- **RLS is the wall.** `FORCE ROW LEVEL SECURITY` on every table with `vendor_id`; `regulars_app` cannot bypass; policies are generated, so a new table is covered on creation. Leak-matrix test: for every tenant table, vendor A's transaction `SELECT count(*)` must be 0 on vendor B's seed rows — generated from `information_schema.columns WHERE column_name='vendor_id'` so the test list can't drift from the schema.
- **Outlet scope** (staff limited to outlets) = second policy on `app.current_outlet_ids()`, v1.1. Column and function exist.
- **Customers global by design**: one `pii.customers` row per human across every outlet — the customer signs in once and is recognised platform-wide (item 67). Customer-facing routes set `app.customer_id` after OTP.
- **The PII wall is a grant, not a convention.** `regulars_app` has no table privilege in schema `pii`; it sees `pii.customer_public` (no phone, no name) and calls `pii.reveal_identity()`, which raises `42501` unless the calling vendor holds a `customer_profiles` row with `revealed_at IS NOT NULL`. Test: a vendor that has never taken an order from customer X must get an exception, not a row. 🧪
- **Reveal on first order** (item 67): `customer_profiles.revealed_at` and `display_name` are written in the **same transaction** as that customer's first `order_placed` at that vendor, and never before. A profile row may exist earlier (created at OTP so history and segments work); until `revealed_at` is set the owner sees counts only. Test: OTP at outlet B, no order → outlet B's customer book shows the visit in aggregate and no name. 🧪
- **Deliberate exceptions to the wall**, both recorded here so nobody 'fixes' them: `bills.customer_phone`/`customer_name` (a GST invoice must carry the buyer, and by definition that customer ordered there) and `conversations`/`messages` (the sender needs a real phone — the `phone` column, and `messages.raw`, are revoked from `regulars_app` by column-level grant; the owner UI masks to `98•••••210`).
- **Anonymous visitors** (item 68): `app.visitors` rows that never link to a customer are deleted once `purge_after` passes (400 days). Browse rows for an unlinked visitor carry no name, no phone and no device fingerprint — only a random uuid and a coarse UA family.
- **Workers** use `regulars_worker` (BYPASSRLS) and must pass `vendor_id` explicitly; an ESLint rule forbids `asWorker` inside `modules/*/…service.ts` except in `jobs/`.
- **Erasure job** (DPDP right to erasure): `pii.customers` → `phone = 'erased:' || sha256(phone)`, name/birthday NULL, `status='erased'`; `pii.customer_refresh_tokens`/`pii.customer_devices` → hard delete (revokes every signed-in device); `customer_profiles` → `display_name` NULL, `phone_hash` NULL, `custom_attributes = '{}'`; `visitors` → `customer_id` NULL (the behaviour stays, anonymised), `browse_sessions.customer_id` NULL; `messages` → `content_text`, `content`, `raw` NULL (UPDATE allowed on partitions via worker role); `bills.customer_phone` → last-4 masked (GST record kept); `events` untouched (no PII by contract, `customer_id` stays so aggregates hold); lake → tombstone file per `customer_id`, compaction job rewrites parquet within 30 days; `customer_consent_events` kept (legal evidence), `audit_logs` row written.
- **Vendor export** (#9): one job → `COPY (SELECT …) TO STDOUT WITH CSV` per tenant table under `regulars_worker` with `WHERE vendor_id = $1`, zipped to Storage, presigned 7 days, audit-logged.

### 4.8 Supabase specifics worth using (and not)

| Use | For | Note |
|---|---|---|
